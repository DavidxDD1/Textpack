# TextPack 设计说明

## 1. 需求边界

目标使用者为需要检索、整理少量文本的课程学习者；需求为场景假设，尚未进行真实用户调查。最小流程是 UTF-8 文本输入、KMP 查询、Huffman 打包、文件下载及还原。核心算法同时向 CLI 和本地网页提供服务，界面层不包含第二套压缩算法。

## 2. 模块与数据流

```text
浏览器输入 / CLI 文件
          |
          v
server.py / cli.py    输入类型、大小与文件路径检查
          |
          v
service.py           组织检索、压缩和还原比较
       /       \
      v         v
kmp.py       codec.py
前缀数组     计数 -> 最小堆 -> 二叉树 -> 码表 -> 位流
位置列表     TPK1 -> 检查 -> 重建树 -> 解码 -> 频次和CRC
      \         /
          v
JSON 结果 / 字节文件 -> 表格、预览、下载
```

表示层使用 `textContent` 和 DOM 文本结点插入输入文本，不把输入解释成 HTML。后端只开放固定静态文件及四个业务接口，无法请求任意本地文件。监听地址固定为 127.0.0.1，校验 Host 与 Origin。此设计用于本机演示，没有实现多用户身份管理。

## 3. KMP 实现要点

`pi[i]` 是 `pattern[:i+1]` 的最长相等真前后缀长度，不使用哨兵 next 数组。构造时，若当前字符不匹配已知最长边界的下一字符，则转向该边界自身的最长边界；回退链覆盖所有可能候选。

文本扫描保持 j 个字符已经匹配。匹配成功时，输出当前位置减模式长度再加 1，并令 `j=pi[j-1]`。例如 `ababab` / `abab`，完整匹配后的 j 为 2，因此可接着找到下标 2。若重置为 0，就会漏掉这次重叠匹配。

Python 字符串按 Unicode 码点索引；浏览器 JavaScript 默认按 UTF-16 单元索引。前端使用 `Array.from(text)` 映射码点，防止 emoji 后的高亮偏移。组合字符不做规范化，`é` 和 `e` 加组合重音不自动视为同一串。

导入的原始字符串存放于 `sourceText`，不会因 textarea 显示自动把 CRLF 改成 LF。仅当用户触发输入事件，才用编辑框的新文本替换它。UI 与 CLI 的字节范围不同，这种差异在 README 中明确说明。

## 4. 二叉 Huffman 与确定性

堆中的元素为 `(weight, min_symbol, node)`。各子树包含的叶集合不相交，最小字节值唯一，因此同频率时也能确定先后顺序。权值更小或同权值下最小字节更小的子树在左。解压器从频率表按同样规则重建树，不需要在文件中存储 Python 对象。

设两个最小权值为 a、b，可以在某棵最优树中把它们交换到最深兄弟叶的位置而不增加加权路径长度。收缩为权值 a+b 的叶后，原代价为收缩后的代价加 a+b；若子问题不是最优，替换即可改善原树，矛盾。这给出反复合并两个最小权值的依据。实验另外用穷举所有合并顺序进行对照，不仅重复验证实现本身。

## 5. TPK1 二进制格式

所有多字节整数使用大端、无符号表示。

| 偏移 | 字节数 | 字段 | 验证规则 |
| --- | --- | --- | --- |
| 0 | 4 | 魔数 `TPK1` | 必须完全相等 |
| 4 | 4 | 原始字节数 B | 不超过配置上限 |
| 8 | 4 | 编码有效位数 L | 必须等于频次与码长的乘积和 |
| 12 | 2 | 不同字节数 σ | 0～256 |
| 14 | 4 | 原始数据 CRC32 | 解码后重新计算 |
| 18 | 5σ | 字节/频次表 | 每项 u8+u32，字节递增，频率为正 |
| 18+5σ | ceil(L/8) | 有效码流及零补齐 | 高位先读，末尾补齐位全为零 |

频率表总和必须等于 B。文件长度必须精确等于计算值，既拒绝截断，也拒绝尾部附加字节。解码后再次比较字节直方图与 CRC32，避免只验证输出长度而漏掉改序或改值。

空文件使用 B=0、σ=0、L=0、CRC32=0，长度为18 B。单字节种类的文件采用码字0，L=B。对 `banana`，频次为 a:3、b:1、n:2；码表 a=0、b=10、n=11；码流为 `100110110`，补零后为十六进制 `9B 00`，整个文件为35 B。

这不是通用交换标准，只保证 TPK1 的当前编码规则。未来改变格式时必须使用新魔数/版本，不能悄悄让旧解码器使用另一种平局规则。

## 6. 开销与取舍

KMP 使用 O(m) 的前缀数组；保存 r 个匹配位置为 O(r)。界面截断显示并不改变后端已经计算的总数，因此最坏 r≈n 时仍需线性结果内存。未来可加入流式迭代器以改变这一点。

Huffman 计数 O(B)，建树 O(σ log σ)，递归创建码字字符串最坏 O(σ²)，编码/解码与输出位数相关，为 O(B+L)。现实现整文件驻留内存，不是流式算法。字节字母表最多256种，树深最多255，小于 Python 默认递归限制。

保存频率的优点是格式直观、可验证且确定性重建容易；缺点是每种字节多付5 B，短文件常变大。没有为负收益文件偷偷切换为另一种格式，因为项目要清楚展示 Huffman 的收益与成本。可以在未来版本添加明确的“原样存储”标志，改善实用性。

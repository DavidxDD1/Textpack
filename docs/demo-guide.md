# 演示与讲解提纲

## 五分钟演示

1. 在干净目录运行 `python main.py serve`，展示程序不需要 pip 依赖。
2. 载入示例，说明49次匹配、12,288 B输入、9,631 B完整文件。展开编码与合并记录。
3. 用 `ababab` / `abab` 展示位置0、2；用 `🙂算法🙂算法` / `🙂算法` 展示位置0、3。
4. 下载 `.tpk`，清空输入，再导入压缩文件还原。随后导入损坏文件，展示拒绝原因。
5. 在终端执行测试，展示实际通过结果，再说明 `banana` 变大以及 gzip 对重复段落更有效的局限。

## 应能解释的问题

| 问题 | 核心解释 |
| --- | --- |
| 为什么完整匹配后不把 j 清零？ | 匹配串后缀可能仍是模式前缀，回退到 pi[j-1] 才保留重叠。 |
| 为什么 Huffman 能解码？ | 码字对应叶路径，任何叶都不是另一叶的祖先，因此是前缀码。 |
| 相同频率如何保证重建相同树？ | 按子树最小字节值打破平局，压缩器和解压器执行同一规则。 |
| Huffman 最优是否意味着文件一定变小？ | 仅针对给定符号频率的前缀编码代价最优，元数据、补齐和未利用的序列相关性仍有开销。 |
| 为什么空文件仍有18 B？ | 文件头记录格式、原始长度、有效位数、符号数量和 CRC。 |
| 检查 CRC32 能否证明数据来自可信作者？ | 不能；这里只检测意外损坏，没有认证或加密。 |
| 为什么 emoji 后的下标容易错？ | Python 码点与 JavaScript UTF-16 单元不等价；本项目统一成码点。 |
| 你本人实际完成了什么？ | 说明选题确认、作业要求、成果核查要求、文档反馈与发布决策，并介绍 Codex 在实现和测试中的辅助作用；结合后续实际复核补充具体例子。 |
